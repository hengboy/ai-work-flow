# 受管提示词排版规范

## 适用范围

本规范适用于仓库管理的 Skill、角色 Agent 正文和路由规则。平台生成器应原样保留这些 Markdown 指令内容。

## 文档结构

- 每份直接提示词使用一个 `#` 主标题，并以语义化 `##` 和 `###` 组织后续内容。只有需要分组多条内容时才使用 `###`；单条规则应并入相邻段落或列表。
- 标题、段落和列表之间保留空行；执行步骤使用有序列表。
- `**加粗**` 仅用于角色名、关键状态和标签，例如 `**状态：**`、`**结论：**`、`**阻塞：**`。

## 回复格式

正常回答按角色使用相应的 `## 回复格式` 和加粗标签列表。目录式 plan/task 的全部实施已完成最终整合与清理，且不存在未解决的 blocking finding 时，Coding 必须明确告知用户“已经全部完成”，并严格按以下顺序使用五段式完成态结构：`**实施结果：**`、`**完成内容：**`、`**验证结果：**`、`**变更范围：**`、`**遗留事项：**`。其中 `**实施结果：**` 必须明确写出“已经全部完成”；`**遗留事项：**` 仅列建议项和未覆盖风险，没有则写“无”，不得写入 blocking finding。

完成态之外，Coding 使用 `**协调状态：**`、`**已委派：**`、`**已收到：**`、`**结论：**` 或 `**阻塞：**` 等旧协调标签汇报非完成态；没有内容的标签应省略。存在阻塞或需要用户决策时，必须使用 `**阻塞：**` 说明原因和所需决策。审查结果中的 blocking findings 与 advisory findings 必须分别放入独立的 `**阻塞项：**` 与 `**建议：**` 区块，不得混在同一区块内。

| 类型 | 必需标签 |
| --- | --- |
| Coding | 完成态使用实施结果、完成内容、验证结果、变更范围、遗留事项；非完成态使用协调状态、已委派、已收到、结论或阻塞 |
| File Explorer 与 Researcher | 发现、代码地图或来源、交接 |
| 写作与实现角色 | 完成、变更、验证或阻塞 |
| 审查角色 | 结论、按严重性分组的发现、测试缺口；Code Reviewer 分列 Standards 与 Spec |
| Git Operator | 提交结果；范围不清时仅输出其固定停止句 |
| 生成、切换与执行 Skill | 结果、更新或状态、注意或阻塞 |

## 受管标记

嵌入用户 `AGENTS.md` 或 `CLAUDE.md` 的受管标记仅是 Markdown 片段，不得注入新的一级标题。
